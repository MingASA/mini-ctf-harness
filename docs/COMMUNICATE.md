# 两台 Harness 的点对点通信

`feature/lan-communicate` 在现有交互式会话上增加一个工具 `communicate`。双方各自正常解题，可以提问、分享发现和回复；收到的消息通过现有 TaskInbox 进入对应主会话，效果类似新收到一条用户消息，但明确标注来源是队友 Agent。

没有 Center/Worker、任务图、自动派工或自动新建会话。每道本地题目只绑定一个对端题目；可以为不同题目分别配对。没有通信配置时不监听网络端口，也不增加工具。

## 配置与启动

两端使用同一分支的代码。已有安装不需要下载新权重、重建镜像或修改模型后端。切换版本前退出该机器上的旧前端，保留原有未提交改动；开发工作树不应替换正在使用的 main。

在 **准备运行此分支的配置文件** 顶层增加 `communicate`：

```json
{
  "communicate": {
    "name": "player-a",
    "host": "0.0.0.0",
    "port": 18765,
    "advertiseUrl": "http://192.168.77.11:18765",
    "secret": "replace-with-the-same-random-secret-on-both-machines"
  }
}
```

队友改成自己的 `name` 和 `advertiseUrl`，例如 `player-b`、`http://192.168.77.12:18765`。这些地址只是当前两台机器的示例，没有写死在程序里。端口可改；监听端口、对外地址端口和防火墙放行端口要一致。

两台机器的 `secret` 相同。可以在一台机器执行 `python3 -c 'import secrets; print(secrets.token_hex(32))'` 生成，再通过你们自己的方式复制到另一台配置。不要把密钥写进提示词或发给模型。

启动使用现有入口 `./mini-ctf`；若准备的是另一份配置，可运行 `./mini-ctf start /绝对路径/config.communicate.json`。不要同时启动两个争用同一模型或会话目录的前端。本次开发没有修改 main 的本地配置，也没有自动启用通信。

`advertiseUrl` 必须是另一台电脑实际能够访问的地址。多网卡、VPN 或 WSL mirrored 模式下请明确填有线 LAN IP；不自动猜测第一张网卡，避免选到 Wi-Fi/VPN 地址。通信只需要这一个 HTTP TCP 端口，不依赖广播发现，不需要开放模型端口。

## 配对并聊天

1. 两人在各自 Harness 中选中要合作的题目，仍各自保留完整对话、工具和工作区。
2. A 输入 `/communicate open`。终端会显示一条包含本机地址和随机会话码的连接命令，例如：

   ```text
   /communicate connect http://192.168.77.11:18765 这里替换成A显示的完整会话码
   ```

3. B 在自己的对应题目中粘贴这条命令。成功后双方都获得 `communicate` 工具，无需反向重复配对。会话码标识明确题目；相同题号不代表同一道题。
4. 直接告诉自己的模型“和队友讨论这个卡点”，模型即可调用：

   ```json
   {"message":"我观察到校验覆盖了长度字段，但不包含末尾四字节。你能从另一种实现验证吗？"}
   ```

   对端会在主会话收到带发送者和会话标识的消息。对端回复也使用 `communicate`；普通最终回答仍只显示在本机。

模型可以继续探索，也可以结束当前回答等待来信。提示词要求交换有价值的证据和问题，避免仅为确认收到而反复回复；Harness 不自动转发全部回答、不持续轮询模型。队友消息作为观察信息，不等同于人工操作者的指令优先级。

| 命令 | 用途 |
| --- | --- |
| `/communicate` | 当前节点、配对、待投递数、失败数、网络错误和重试时间 |
| `/communicate open` | 开放当前题目，显示可复制的对端连接命令 |
| `/communicate connect URL 会话码` | 双向配对；断线回执丢失时可重复执行 |
| `/communicate send 消息内容` | 人工直接向对端 Agent 发消息，无需先让本机模型生成 |
| `/communicate messages` | 查看当前会话最近的收发消息和投递状态 |
| `/communicate off` | 当前题目停止通信，取消尚未发出的消息 |
| `/tab output`、`/tab inbox` | 查看对话或已收到、待模型处理的消息 |

`communicate({"action":"status"})` 让模型检查本地投递状态；不必不停查询，回复会自动入队。没有设置消息长度硬上限，仍应发送简洁、充分的上下文。关闭后重新 open 会生成新的会话码，防止旧队友消息进入新绑定；更换对端前也要先 off。

## 生成、暂停与故障处理

- 正在生成时收到消息：写入收件箱，在后续请求中加入，不启动第二个主 Agent，不插入半截工具结果。
- 正常等待输入时：消息把对应题目加入原有调度队列。不会切换人类正在查看的题目，也不直接抢占另一道正在生成的题目。
- 人工暂停、工具结果待核查、预算耗尽或已判正确：消息保留，但不自动恢复。用原有 `/resume`、必要时 `/start` 继续。关闭模型服务或停止整体调度也不会被远端擅自恢复。
- 发送先写入本地持久化发件箱。连接超时、断网、对端重启会自动重试，连续失败逐步延长间隔至约 30 秒；不会因为网络断了就在工具内卡住解题。
- 同一条消息使用固定 ID。回执丢失、重发、重启恢复不会重复插入已接受的消息。接收节点 ID 与双方会话 ID 都必须匹配，IP 被别的机器复用不会悄悄改投。
- `queued` 表示本地排队；`delivered` 只表示对端收件箱已持久化接收，**不表示模型已经读完或回复**。
- 明确的会话关闭、节点不匹配等错误会记为 `failed`，并将失败通知放入发送方会话；不会假报送达，也不会阻塞其他题目通信。网络临时错误继续重试，不给模型反复塞错误通知。
- `off` 无法撤回已经送达的消息。停止前已进入网络的请求也可能已经被对端接受。

状态保存在 `contestDir/communication/`，原始题目消息仍在原来的会话日志。不要把整份节点身份目录复制给另一台机器。重启会恢复配对、收件去重和未确认发件箱；已落盘但工具返回尚未记完的 `communicate` 会依据原收据恢复，不重新执行发送工具。

如果 IP 变了，修改本机通信配置并重启，然后在原配对题目重新执行 connect，使用对端的新地址和原会话码；身份相符时更新投递地址，未确认消息继续补发。更换机器或清空节点状态则需要重新配对。

## 网络检查与边界

- Ping 不通时先查两端网线、网卡连接状态、IP/掩码和路由。程序能在链路恢复后补发，无法修复网线掉线。
- Ping 通但 connect 超时：确认对端 Harness 已启动通信监听；Windows/WSL 防火墙需放行配置的 TCP 端口。可在 Windows 用 `Test-NetConnection 对端IP -Port 18765` 验证 TCP，不能用 Ping 代替端口测试。
- `authentication failed`：核对共享密钥；`session ... closed`：重新取得对端 open 的会话码；`EADDRINUSE`：端口已被其他进程占用，选择空闲端口并同步改地址。
- 不需要关闭防火墙、改 Docker 网络或开放 llama-server。这个工具由宿主机 Harness 执行，解题容器即使是 `network=none` 也可以使用通信工具。
- 当前版本只传文字，不自动传文件、同步文件系统或远程执行命令。文件可沿用你们已有的局域网传输方式；消息里注明文件来源，不能假定远端 `/work/...` 是本地文件。
- `/btw` 保持本地独立讨论，没有 `communicate` 工具，也不会收到新的对端消息。通信命令请先 `/main`，确保准确路由到主会话。

协议用于可信局域网，共享令牌 HTTP，无互联网服务依赖。没有自动连接其他机器，不会接触未指定的 `.14`。
